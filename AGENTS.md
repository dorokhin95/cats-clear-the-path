# ГЛОБАЛЬНЫЕ ПРАВИЛА РАБОТЫ

Эти инструкции действуют всегда для всех задач в данном проекте.

## 1. Язык

Все ответы пользователю, планы, отчёты о выполненной работе и проектная документация должны быть на русском языке.

Код, имена переменных, функций, классов, API, библиотек, путей, команд и технических сущностей должны следовать существующим соглашениям проекта. Не переводить их на русский без необходимости.

## 2. Перед началом любой задачи

Сначала:

1. Определи, что именно требуется сделать.
2. Разбей задачу на логические подпункты.
3. Составь короткий план выполнения.
4. Определи, какие части проекта могут быть затронуты.
5. Проверь существующую документацию проекта.

Для очень маленьких задач план может состоять из 1–3 пунктов.

Не начинай вносить изменения до понимания задачи и структуры затрагиваемой части проекта.

## 3. Documentation First

Документация проекта является основной картой проекта.

Перед поиском реализации в исходном коде сначала изучай существующую документацию:

- README
- PROJECT_MAP / структура проекта
- ARCHITECTURE
- документацию конкретного модуля
- DECISIONS / принятые архитектурные решения
- CHANGELOG / историю изменений
- другую связанную документацию

По документации сначала определяй:

- где находится нужная функциональность;
- какие файлы за неё отвечают;
- как она взаимодействует с другими частями проекта;
- какие ограничения существуют;
- какие решения были приняты ранее.

После этого открывай только те файлы исходного кода, которые относятся к задаче.

Не читай весь проект без необходимости.

## 4. Документация не является непроверяемой истиной

Если документация:

- отсутствует;
- неполная;
- устарела;
- противоречит фактическому коду;

тогда необходимо изучить минимально необходимый участок кода, установить фактическое поведение системы и сразу обновить документацию.

Нельзя оставлять обнаруженное расхождение между кодом и документацией неисправленным.

## 5. Документация всегда должна быть актуальной

Любое изменение проекта, которое влияет на:

- архитектуру;
- структуру;
- поведение;
- API;
- зависимости;
- конфигурацию;
- файлы;
- интерфейсы;
- процессы запуска;
- сборку;
- тестирование;
- важные технические решения;

должно сопровождаться обновлением соответствующей документации.

Если в процессе работы первоначальное решение изменилось, документация должна быть обновлена в соответствии с итоговой реализацией.

После завершения задачи документация должна описывать текущее состояние проекта, а не первоначальный план.

## 6. Документирование новой функциональности

При создании нового инструмента, функции, модуля, сервиса, продукта или значимого участка кода документируй:

- что это;
- зачем это существует;
- где расположено;
- какие файлы отвечают за реализацию;
- как оно работает;
- от чего зависит;
- какие данные принимает;
- что возвращает;
- с какими компонентами взаимодействует;
- как запустить;
- как проверить;
- какие есть ограничения;
- какие важные решения были приняты.

Документация должна позволять другому разработчику найти нужную реализацию без чтения всего проекта.

## 7. Минимальные изменения

При выполнении задачи изменяй только то, что необходимо для её решения.

Не выполняй без необходимости:

- глобальный рефакторинг;
- переименование несвязанных сущностей;
- изменение форматирования всего проекта;
- замену библиотек;
- изменение архитектуры соседних модулей;
- удаление существующего функционала.

Если для задачи требуется крупное архитектурное изменение, сначала объясни его необходимость.

## 8. Проверка после изменений

После каждого изменения обязательно проверь результат.

В зависимости от проекта используй доступные средства:

- unit tests;
- integration tests;
- build;
- typecheck;
- lint;
- formatter;
- запуск приложения;
- ручную проверку поведения.

Если автоматическая проверка невозможна, явно укажи, что и как было проверено вручную.

Нельзя объявлять задачу завершённой только потому, что код был изменён.

## 9. Не делать предположения без проверки

Если неизвестно:

- где находится функциональность;
- как работает модуль;
- существует ли файл;
- используется ли зависимость;
- какой API доступен;
- какое поведение ожидается;

не делай предположение фактом.

Сначала проверь документацию, затем при необходимости код, конфигурацию или окружение.

## 10. Новые зависимости и крупные изменения

Не добавляй новые внешние зависимости без необходимости.

Перед:

- добавлением крупной зависимости;
- сменой фреймворка;
- изменением архитектуры;
- миграцией данных;
- удалением значительных частей проекта;
- изменением публичного API;
- выполнением потенциально разрушительных действий;

объясни необходимость и запроси подтверждение, если это не было явно поставлено задачей.

## 11. Работа с ошибками

Если во время выполнения задачи обнаружена другая ошибка, не связанная напрямую с текущей задачей:

1. зафиксируй её;
2. опиши кратко;
3. не начинай большой побочный рефакторинг без необходимости.

Если ошибка блокирует текущую задачу — исправь её минимально необходимым способом и задокументируй.

## 12. Завершение задачи

Перед завершением обязательно:

1. Проверь, что выполнены все пункты первоначального плана.
2. Проверь результат работы.
3. Проверь, что ничего очевидного не сломано.
4. Обнови связанную документацию.
5. Убедись, что документация соответствует итоговому коду.

В итоговом сообщении укажи:

- что было сделано;
- какие файлы изменены;
- какие важные решения были приняты;
- как результат был проверен;
- какую документацию обновили;
- остались ли известные ограничения или незавершённые пункты.

## 13. Главный принцип

Работай по циклу:

ЗАДАЧА  
→ ПЛАН  
→ ДОКУМЕНТАЦИЯ  
→ ТОЧЕЧНОЕ ИЗУЧЕНИЕ КОДА  
→ ИЗМЕНЕНИЯ  
→ ПРОВЕРКА  
→ ОБНОВЛЕНИЕ ДОКУМЕНТАЦИИ  
→ ФИНАЛЬНАЯ ПРОВЕРКА  
→ ОТЧЁТ  

Документация проекта должна в любой момент позволять понять архитектуру проекта и найти нужную реализацию без необходимости читать весь исходный код.
