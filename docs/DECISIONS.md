# Журнал архитектурных решений (Architecture Decision Records)

В данном документе фиксируются ключевые технические и архитектурные решения проекта, их контекст, аргументация и последствия.

---

## ADR-001: Разделение отрисовки: Canvas для геймплея, HTML/CSS для интерфейса
- **Статус:** Принято.
- **Контекст:** Требуется мобильная игра с высокой частотой кадров (60 FPS), анимациями сжатия котиков и частицами, но с удобным, гибким и локализуемым интерфейсом.
- **Решение:** 
  - Игровое поле, персонажи, следы лапок и анимации рисуются на одном легковесном элементе `<canvas>`.
  - Все кнопки, экраны меню, модальные окна, настройки и HUD реализуются через семантический HTML5 и CSS3.
- **Последствия:** Отличная адаптивность интерфейса под любые экраны, простота стилизации, нулевая нагрузка на Canvas от статических элементов меню.

## ADR-002: Отказ от тяжелых фреймворков и движков (No React / No Phaser / No Pixi)
- **Статус:** Принято.
- **Контекст:** Проект ориентирован на мгновенную загрузку в браузере (Яндекс Игры, мобильный веб). Движки вроде Phaser или PixiJS добавляют от 500 КБ до 1.5 МБ в бандл и замедляют cold start.
- **Решение:** Чистый TypeScript + Vite + нативные Canvas 2D API и WebAudio API.
- **Последствия:** Размер бандла менее 150 КБ, мгновенный старт, полный контроль над кодом, простота отладки и поддержки.

## ADR-003: Процедурная отрисовка котиков на первом этапе разработки
- **Статус:** Принято.
- **Контекст:** Рисование десятков растровых спрайтов для разных направлений и скинов затягивает старт проверки кор-геймплея.
- **Решение:** Котики на этапе прототипа и первой версии рисуются процедурно через векторные примитивы Canvas 2D (`arc`, `bezierCurveTo`, сглаженные формы).
- **Последствия:** Возможность моментально отладить анимации squash/stretch, масштабирование под Retina/DPR без пикселизации, легкая смена палитр и скинов.

---

## ADR-004: Использование процедурного звука через WebAudio API для MVP
- **Статус:** Принято.
- **Контекст:** Загрузка внешних аудиофайлов mp3/wav требует управления сетью, прелоадера и увеличивает вес бандла.
- **Решение:** Реализовать легковесный синтезатор звуков на WebAudio API (`OscillatorNode`, `GainNode`).
- **Последствия:** Нулевая задержка воспроизведения, динамическое управление питчем для комбо-эффектов, отсутствие внешних сетевых зависимостей.

## ADR-005: Валидация уровней методом «Солвер в первую очередь» (Solver-First)
- **Статус:** Принято.
- **Контекст:** В головоломках с блокировкой путей случайная расстановка может создавать нерешаемые тупики (deadlocks).
- **Решение:** Создать `LevelSolver` до написания генератора. Все уровни (ручные и генерируемые) проходят обязательную 100% валидацию солвером.
- **Последствия:** Невозможность попадания в продакшн нерешаемого уровня, автоматизация юнит-тестирования.

## ADR-006: Изоляция платформ через паттерн «Адаптер» (Web, Telegram, Yandex)
- **Статус:** Принято.
- **Контекст:** Игра публикуется сначала на автономном Вебе (GitHub Pages), затем как Telegram Mini App, а позже — на Яндекс Играх. Принудительное подключение Яндекс SDK в `index.html` ломало автономность и генерировало сетевые ошибки.
- **Решение:** Выделить модуль `src/platform/` с единым контрактом `PlatformService`. Реализованы `WebPlatformService` (дефолт), `TelegramPlatformService` (BackButton, haptics, safe-area) и `YandexPlatformService` (динамическая подгрузка SDK по требованию).
- **Последствия:** Ядро игры полностью отвязано от платформенных API. Сборка универсальна для любых сред.

## ADR-007: Постраничная организация глав в LevelSelect (10 карточек на главу)
- **Статус:** Принято.
- **Контекст:** Прежний бесконечный вертикальный список уровней создавал визуальный шум, требовал долгого скролла и ухудшал UX на мобильных экранах.
- **Решение:** Разбить прогрессию на главы строго по 10 уровней с пагинацией `◀`/`▶`, индикатором звёзд `⭐ X / 30` и сохранением открытой главы.
- **Последствия:** Четкая порционная структура уровней, адаптивность сетки до 320px, удобная навигация без скролла.

## ADR-008: Изоляция Canvas при открытых полноэкранных меню
- **Статус:** Принято.
- **Контекст:** Под полупрозрачными меню просвечивало игровое поле, а `requestAnimationFrame` продолжал холостой рендеринг на мобильных устройствах.
- **Решение:** Сделать все полноэкранные экраны непрозрачными (`.ui-screen--opaque`), скрывать слой холста (`.canvas-layer.hidden`) и пропускать фазу `render()`, пока активно меню.
- **Последствия:** Чистый визуальный стиль без артефактов наложения, экономия батареи мобильных устройств.

---

## ADR-009: Схема сохранений V2 и многофакторный Performance-скоринг
- **Статус:** Принято.
- **Контекст:** Оценка прохождения только по оставшимся жизням была примитивной и не стимулировала перепрохождение уровней.
- **Решение:** Внедрить расчет мастерства (0–100 баллов) с учетом скорости (таймер от первого тапа), комбо (окно 4.5с) и ошибок. В схеме V2 сохранять персональные рекорды для каждого уровня с безопасной автомиграцией старых сохранений V1.
- **Последствия:** Высокая реиграбельность, динамичный азарт от комбо без стрессовых таймеров на старте, 100% сохранность данных существующих игроков.
